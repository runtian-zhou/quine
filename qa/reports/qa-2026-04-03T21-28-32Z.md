## Root-Cause Notes

Implementation inspection shows `refresh_in_flight` is set to `true` in `crates/quine-core/src/engine.rs` when scheduling background summary refresh:

- `crates/quine-core/src/engine.rs:72`

but no corresponding code clears `refresh_in_flight` back to `false` after the background task finishes. `should_refresh_summary` explicitly refuses refresh when `refresh_in_flight` is true:

- `crates/quine-core/src/memory/summary.rs:69-75`

This matches the live-daemon symptom: first refresh runs, later turns in the same process are skipped indefinitely until a restore path reconstructs fresh state with `refresh_in_flight = false`.

## Risks and Residual Concerns

- The in-process `quine-core` integration tests do not catch the live-session regression because they likely recreate or restore session state differently from the long-lived daemon path.
- As implemented, summary maintenance can silently stall for the remainder of a daemon session after the first successful refresh.
- Workspace CI would fail until the `PersistedSession` initializer in `quine-harness` tests is updated.

## Recommended Follow-up

1. Fix the runtime state transition so session-memory refresh completion reliably clears in-flight state for the session in the live daemon path.
2. Add or adjust a daemon-equivalent or long-lived-session test that proves multiple turns in one process advance session-memory state more than once.
3. Update `crates/quine-harness/src/storage.rs` test fixtures to include the additive `memory_state` field or otherwise use a constructor/default path compatible with the new persisted schema.
